# 02 — Схема сценария (JSON)

Это формат файла, который импортируется в Bot Builder. Источник истины — дословная
спецификация в [canonical/platform-spec.md](canonical/platform-spec.md).

## Корневая структура

```json
{
  "name": "Название бота",
  "description": "Краткое описание",
  "config": {
    "id": "my-bot-machine",
    "initial": "start",
    "context": {
      "user_name": "",
      "user_choice": "",
      "manager_id": ""
    },
    "states": {
      "start": { "...": "..." },
      "end_node": { "type": "end" }
    }
  }
}
```

| Поле | Тип | Назначение |
|---|---|---|
| `name` | string | Имя бота (видно в списке «Мои боты»). |
| `description` | string | Описание. |
| `config.id` | string | Идентификатор машины состояний (напр. `my-bot-machine`). |
| `config.initial` | string | Стартовый узел. Практически всегда `"start"`. |
| `config.context` | object | Начальные переменные. Объявляй здесь все переменные, которые используешь (пустыми строками), включая служебные вроде `manager_id`. |
| `config.states` | object | **Словарь нод**: ключ = id узла, значение = объект узла. |

## Узел (state)

```json
"welcome": {
  "type": "message",
  "data": { "...": "поля под тип узла" },
  "transitions": [ { "...": "переход" } ]
}
```

- `type` — один из 9 типов (см. [03 — Справочник типов нод](03-Справочник-типов-нод.md)).
- `data` — параметры узла, набор полей зависит от `type` (у `start`/`end` обычно нет `data`).
- `transitions` — массив переходов. **Нет у узла `condition`** (там вместо них `trueTarget`/`falseTarget`)
  и у `end` (конечный).

## Переход (transition)

```json
{
  "id": "go-lead",
  "regex": "/Оставить заявку/i",
  "priority": 1,
  "description": "Лид",
  "targetNodeId": "collect_name",
  "unconditional": false
}
```

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | Уникальный id перехода (любая строка/uuid). |
| `regex` | string | JS-RegExp, по которому сообщение пользователя матчится на этот переход. |
| `priority` | number | Порядок проверки: **меньше = выше приоритет**. Конкретные 1–10, fallback `".*"` → `>= 100`. |
| `description` | string | Подпись связи на холсте (на логику не влияет). |
| `targetNodeId` | string | Куда перейти. Должен существовать в `states`. |
| `unconditional` | bool | Если `true` — переход выполняется **сразу**, без ожидания ввода пользователя. |

Подробно про логику матчинга — [04 — Переходы, regex, приоритеты](04-Переходы-regex-приоритеты.md).

## Жёсткие правила валидности

- Сценарий **обязан** иметь узел `start` и узел `end`.
- Все `targetNodeId` (а также `trueTarget`/`falseTarget` у `condition`,
  `invalidAttemptsTargetNodeId` у `message`) должны ссылаться на существующие ключи в `states`.
- `condition`-узлы **не имеют** `transitions` — только `trueTarget` и `falseTarget` внутри `data`.
- `saveVariable` сохраняет ответ пользователя в `context`.
- Подстановка `{varName}` работает в: `message`, `http.url`, `http.body`,
  `notify_user.recipientId`, `notify_user.message`.
- Переход с `"unconditional": true` выполняется немедленно (цепочки авто-сообщений).
- regex — синтаксис JavaScript RegExp (`"/.../i"`), **не** инлайновые флаги `(?i)`.

## Минимальный валидный сценарий

```json
{
  "name": "Новый бот",
  "description": "",
  "config": {
    "id": "new-bot-machine",
    "initial": "start",
    "context": {},
    "states": {
      "start": {
        "type": "start",
        "transitions": [
          { "id": "061ddd2e", "regex": ".*", "priority": 0,
            "description": "Начальный переход", "targetNodeId": "end" }
        ]
      },
      "end": { "type": "end" }
    }
  }
}
```
