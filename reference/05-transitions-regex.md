# reference/05 — Переходы, regex, приоритеты

## Переход

```json
{ "id": "uuid", "regex": "/Да/i", "priority": 1, "description": "Подпись на связи",
  "targetNodeId": "node_id", "unconditional": false }
```

| Поле | Тип | Назначение |
|---|---|---|
| `id` | string | Уникальный id (любая строка/uuid). |
| `regex` | string | JS RegExp для матчинга ввода пользователя. |
| `priority` | number | Порядок проверки: **меньше = выше**. |
| `description` | string | Подпись связи на холсте (на логику не влияет). |
| `targetNodeId` | string | Куда перейти (должен существовать). |
| `unconditional` | bool | `true` → выполнить сразу, без ожидания ввода. |

## Алгоритм выбора (по приходу сообщения)

1. Переходы текущего узла сортируются по `priority` (0,1,2,…,100).
2. Берётся **первый**, чей `regex` совпал с вводом.
3. Переход в его `targetNodeId`.
4. Совпало несколько regex → выигрывает меньший `priority`.
5. Не совпало ничего → обработка невалидного ввода (`enableErrorHandling`) или fallback `".*"`.

## Приоритеты — практика
- Конкретные переходы: `priority` 1–10.
- Fallback `"regex": ".*"`: `priority >= 100`.
- Не делай fallback с низким приоритетом — он перехватит конкретные.
- Не дублируй `priority` в одном узле (неоднозначный порядок).

## regex = JavaScript RegExp
✅ `"/да|интересно/i"` · `"/^[\w.-]+@[\w.-]+\.[a-z]{2,}$/i"` · `".*"`
❌ `"(?i)да"` · `"(?i)(да|нет)"` — инлайн-флаги ломают сценарий.

Подсказки:
- `i` — без учёта регистра (почти всегда для текста/команд).
- **reply-кнопки** → regex по **тексту** кнопки. **inline-кнопки** → regex по **`callback_data`**.
- `".*"` матчит всё — только как fallback с высоким `priority`.

## Безусловные переходы
`"unconditional": true` — выполняется немедленно. Нужны:
- после служебных узлов (`http`, `notify_user`, `action`, `schedule_message`, `clear_scheduled_messages`);
- для цепочек авто-сообщений (несколько `message` подряд без ожидания ввода).

Цепочка безусловных «пробегается» мгновенно до первого узла, который ждёт ввод.

## Обработка невалидного ввода (`message`)
- `enableErrorHandling: true` — включает логику.
- `invalidInputMessage` — текст при несовпадении.
- `maxInvalidAttempts` — лимит попыток до увода.
- `invalidAttemptsTargetNodeId` — куда увести после лимита.
- Без `maxInvalidAttempts` бот просто повторяет `invalidInputMessage`.

⚠️ **Проверено вживую (важно):** `invalidInputMessage` показывается ТОЛЬКО когда не совпал ни
один `regex`. Если у узла есть catch-all переход `".*"` (даже с `priority` 100) — он матчит
любой ввод первым, и обработчик невалидного ввода НЕ запускается. То есть на одном узле имеет
смысл одна из двух стратегий обработки нераспознанного ввода:
1. **fallback-переход** `".*"` (priority ≥ 100) → повтор вопроса/меню (мягкий UX), или
2. **`invalidInputMessage`** + `maxInvalidAttempts` + `invalidAttemptsTargetNodeId` — но тогда
   НЕ добавляй `".*"`-переход, иначе обработчик не сработает.
